# Task 31.4 — JSON API: encrypted database unlock flow

Parent spec: `2026-08-06-epic-31-architecture.md` (locked-state section).

**Objective:** web equivalent of the splash-screen password gate, using the
existing primitives: `db::is_encrypted`, `db::validate_password`,
`db::set_db_password`.

## Endpoints

- `GET /api/status` → `{ initialized, encrypted, locked, companyName,
  version, dataDir }` (camelCase; `companyName` null while locked — reading it
  requires the key; `version` = crate version for the SPA's about/update UI).
  Always available once the session cookie is valid.
- `POST /api/unlock` `{ password }` →
  - success: `{ locked: false }`; side effects: `set_db_password(Some(pw))`,
    then open a connection and run `init_db` (the migrations deferred by 31.3
    for encrypted DBs), reset the failure counter.
  - failure: 401-style body but code `invalid_password`, with
    `{ attemptsRemaining, retryAfterMs }`.
- Locked guard: a middleware/extractor on every data route (31.5+ mount under
  it) returns 423 `locked` while `is_encrypted && !unlocked`. This task adds
  the guard plus a marker so later tasks just mount inside the guarded router.

## Backoff

In-memory (AppState) failure counter: attempts 1–3 respond immediately-ish
with `attemptsRemaining`; from attempt 3 on, enforce exponential delay
(1s, 2s, 4s… capped at 30s) server-side before responding — mirror of the TUI
three-attempt posture without a hard lockout (the desk user can always restart
the process). Counter resets on success. No persistence.

## Constraints

- The password must never appear in logs, error messages, or `Debug` output of
  request types (implement `Debug` by hand or skip the field).
- `validate_password` distinguishes wrong-password (`Ok(false)`) from I/O
  errors — map the latter to 500, not `invalid_password`.
- Unencrypted DBs: `status.locked` is false from startup; `POST /api/unlock`
  returns 400 `bad_request` ("database is not encrypted").
- Unlock state is process-wide (the existing global) — document in code that
  serve assumes a single DB per process (matches CLI behavior).

## Tests

Integration tests against a tempdir DB in each state: unencrypted (no gate),
encrypted-locked (status right, data route 423, unlock wrong-password
decrements attempts + backoff grows, unlock success flips status and data
routes work), migrations run on unlock (create an old-schema encrypted DB,
assert `schema_version` bumps after unlock). Uses `open_connection` +
`encrypt_database` helpers from `cli/password.rs`; serial with the password
global (`--test-threads=1` note applies).
