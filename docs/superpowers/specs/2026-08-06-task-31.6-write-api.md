# Task 31.6 — JSON API: write endpoints (edits, review, CRUD, categorize, reconcile, undo)

Parent spec: `2026-08-06-epic-31-architecture.md`. All routes inside the
locked guard; all mutations rejected while locked (423).

## Transaction edits (reviewer.rs is already clean)

- `PATCH /api/transactions/:id` `{ categoryId?, vendor?, flag? }` — applies
  whichever fields are present via `update_transaction_category`,
  `update_transaction_vendor` (null vendor clears), `toggle_transaction_flag`
  is instead exposed as explicit `flag: bool` (fetch current, toggle only if
  different) so the API is idempotent. 404 on unknown id. Returns the updated
  register row (`get_transaction_by_id` shape + flag state).

## Review

- `GET /api/review/queue` → `reviewer::get_flagged_transactions`.
- `GET /api/review/:id` → `get_transaction_by_id` (re-review by id; 404 like
  the CLI's error).
- `POST /api/review/:id/apply` `{ categoryId, vendor?, createRule?,
  rulePattern? }` → `apply_review`, returns `{ ruleId }` (null unless a rule
  was created).
- `POST /api/review/:id/undo` `{ ruleId? }` → `undo_review` (re-flags,
  deletes the rule) — powers the SPA's back navigation (31.13).

## Accounts / categories / rules CRUD

- Accounts: `POST /api/accounts` (add), `PATCH /api/accounts/:id` (rename),
  `DELETE /api/accounts/:id`. Delete keeps the existing hard-delete +
  transaction-count guard; a blocked delete is 409 `conflict` with
  `details: { reason: "has_transactions", count }` — extract the count check
  so the reason is structured, keep the human message.
- Categories: `POST`, `PATCH /api/categories/:id` (all fields via
  `update_category`), `DELETE` (soft). `blocking_reason` gains a structured
  sibling (`blocking_reason_code(&Connection, id) -> Option<(BlockReason,
  i64)>` or refactor it to return a small struct) so the API returns
  `{ reason: "has_transactions" | "has_active_rules", count }`; TUI keeps its
  message.
- Rules: extract the missing data layer per the epic contract —
  `add_rule`, `update_rule` (partial), `deactivate_rule`, all
  `&Connection`-based, with `cli/rules.rs` CLI wrappers delegating to them.
  Routes: `POST /api/rules`, `PATCH /api/rules/:id`, `DELETE /api/rules/:id`
  (soft). Category referenced by **id** in the API (the CLI resolves names;
  the data layer takes id — CLI wrapper does the name lookup).
- `rules_manager.rs`'s inline `UPDATE rules SET is_active = 0` switches to the
  shared `deactivate_rule`.

## Rule test, categorize, reconcile, undo

- `POST /api/rules/test` `{ pattern, matchType }` → **new**
  `rules::test_pattern(&Connection, pattern, match_type) ->
  Result<RuleTestResult { matches: Vec<{ description, count }>, total }>` —
  the existing `test()` computes exactly this then prints it; refactor so CLI
  and API share it. Invalid matchType/regex → 400.
- `POST /api/categorize` → `categorizer::categorize_transactions` →
  `CategorizeResult`.
- `POST /api/reconcile` `{ account, month, statementBalance }` →
  `reconciler::reconcile` (POST because it INSERTs). Unknown account 404;
  `NoTransactions` → 409 with code `no_transactions`.
- `GET /api/reconciliations?account=` → new query over the
  `reconciliations` table (needed by 31.17's history display).
- `DELETE /api/imports/:id` → `undo::delete_import` (404 if absent), returns
  `{ deletedTransactions }`.
